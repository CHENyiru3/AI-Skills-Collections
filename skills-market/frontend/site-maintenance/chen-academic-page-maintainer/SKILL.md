# CHEN Academic Website Maintenance

Use only the user-identified website repository or explicit adoption of this workflow.
Check the real site/configuration and relevant local instructions before applying
saved paths or rules. Do not select an unrelated al-folio repository by similarity.

Read `references/repo-map.md` only when locating sources, `edit-rules.md` for a
protected change, `content-contracts.md` for the affected section, and
`style-preferences.md` when changing prose/design. Load `skill-evolution.md` only
when maintaining this skill; ordinary site work does not require page-keeper or
five mandatory reference reads.

## Retain the site's contracts

- Preserve identity, affiliation, degree/advisor/scholarship wording, future plans
  and publication status from exact user evidence. Supplied wording/authorization
  is sufficient; ask only when a consequential ambiguity remains.
- Prefer source data/shared renderers to duplicate visible-page edits. Check the
  affected mirrors across homepage, CV, publications, projects, timeline and news.
- Retain publication categories/order and full author lists unless changed by the
  request. Derive the current CV PDF from `_config.yml` `cv_pdf_filename` and verify
  filename-based display dates/links; do not hardcode a stale asset/date.
- Keep the homepage version label `Yiru's Version` unless the user changes it.
- Keep Tech Blog `/tech-blog/` and its feed filtered to intentionally tagged/
  categorized tech posts, excluding samples. Requested English/Chinese versions
  normally form one English-default bilingual post. Preserve responsive images
  and disable sample related-post blocks unless wanted.
- Life galleries use confirmed user-provided photos; keep missing-image sections
  text-only rather than fabricating frames or publishing unconfirmed URLs.
- Keep Research Radar distinct from milestone News. Preserve digest article facts,
  category/provider/generator metadata, optional hot-topic hint and the labeled
  Friday BioTech exception. This site's renderer does not imply moving generator,
  ranking, Zotero or RSS automation into the repository.

## External notes and scope

Locate any Website Management workspace from the actual task context. Read its
`Website Source Map.md` for mappings; notes are drafts/mirrors, while the website
source determines rendering. Apply only requested candidates, excluding README,
current landing-page mirrors and templates from automatic post creation. Research
Radar is outside this mirror workflow. Do not initialize a nested notes repository
or stage unrelated notes. No historical absolute user path is required.

Make routine reversible decisions within known authorization. Preserve existing
routes/layout by default; major restructuring and changed protected facts need that
scope in the user request, not a newly invented blanket approval rule. Validate
only affected source/asset links, renderers, feed filters and mirrored facts.
Stop when the requested site change is correct; recording a permanent new skill
rule, committing or publishing is separate unless included.
